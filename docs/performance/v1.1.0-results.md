# v1.1.0 results: performance guard and the cnn_fer workload

Verdict: **no regression.** Against the v1.0.0 tag, built in the same session, no guarded row is more than 0.5% slower in the quiet paired runs (native or portable), and the 8-run suite medians differ by at most +4.3% on one noisy row (infer_nograd_b256 native, 10 to 17% spread) that the paired runs put at 0.995. `ctest` passes in both build dirs (287/287 each) and `bench_tests` passes (12/12) in both.

Old: tag `v1.0.0` in a worktree, built Release into separate native (`NN_NATIVE=ON`) and portable (`NN_NATIVE=OFF`) dirs. New: the v1.1.0 branch, same flags. Machine: Intel i5-12450HX, CPU governor `powersave`, a desktop session (browser, shell) running, so the machine was quiet but not idle. Protocol: `NN_NUM_THREADS=8 taskset -c 0-7`, 15 timed runs per row after 3 warm-ups.

## The odd 2x on cnn_mnist: process history, not load

Mid-branch, cnn_mnist appeared to run about twice as fast as before. In the paired runs the same binary gives 5.2 ms (native) when `cnn_mnist` is the only workload in the process and 2.7 ms when it runs in the full suite after `mlp_wide`; old and new agree in both states, so it is not the code change. The 5.2 ms state is steady (200 runs, 200 warm-ups: 5.07 to 5.10 ms), and setting `MALLOC_MMAP_THRESHOLD_`, `MALLOC_TRIM_THRESHOLD_` and `MALLOC_TOP_PAD_` large brings the isolated run to 2.67 ms. So the step time depends on glibc malloc state: after the large tensors of earlier workloads the dynamic mmap threshold has grown, and fresh per-step tensors are reused from the heap instead of being mapped, zero-filled and unmapped every step (`malloc`, `cfree`, `operator new` and `memset` rows in the profile below). That also means the headline cnn_mnist number depends on what ran before it. This is a finding, not a fix: a buffer-reusing allocator is listed under follow-ups. Load noise alone did not produce it: the paired runs were taken one after another under the same load.

### Diagnosis: why forward is slower than backward

This section describes the state before the broadcast fast path (see below); `elementwise` no longer behaves as described here.

The convolutions are not the cost: `micro_avx2` plus im2col is about 6% of samples. More than half of the samples (about 60% with malloc and free) are in the binary elementwise ops `mul`, `sub` and `add` and in the generic-broadcast helper `unravel_index`. `BatchNormBase::forward` in training mode is built from those ops on `[N, C, H, W]` tensors against `[1, C, 1, 1]` statistics, about ten full-tensor passes per layer. In `src/tensor.cpp`, `elementwise` never uses the thread pool, and its fast paths (`broadcast_small`) cover only a scalar, a trailing block and a last-axis column. A `[1, C, 1, 1]` operand matches none of them, so every such op takes the general path: one `unravel_index` call per element, which allocates a `std::vector` each time (the malloc/free/new rows), then `broadcast_offset` for both operands. The three BN layers see 2.36 M, 1.18 M and 0.59 M elements per tensor at batch 64 (64x16x48x48, 64x32x24x24 and 64x64x12x12 floats), so this adds up to hundreds of milliseconds, and it is serial, which matches the flat thread sweep.

Backward is faster because the gradient of a broadcast op only has to reduce back to the small shape through `Tensor::operator+=`/`reduce_axis`, which do run on `parallel_range`, and because backward does not recompute the mean and variance reductions. Backward is not parallel either (270 ms at 1 and at 12 threads): the same serial elementwise ops sit inside its closures (for example `mul` backward). This diagnosis rests on the profile and the thread sweep. The fix is a channel-broadcast fast path plus `parallel_range` over the equal-shape path, described next.

## Broadcast fast path

`elementwise` in `src/tensor.cpp` now computes the result shape and one stride per operand once (0 on broadcast or missing axes), merges adjacent axes that both operands walk contiguously, and runs a tight loop over the innermost merged axis with an incrementing index over the outer axes. No allocation happens per element. The output is split into disjoint flat ranges with `kernels::parallel_range` (same threshold as `+=`), so results do not depend on the thread count. The scalar, row and column fast paths and the equal-shape loop are folded into this one path. The arithmetic per element is unchanged; `tests/test_tensor.cpp` checks add, sub, mul and div bitwise against an index-by-index reference for many shape pairs and 1, 3 and 8 threads. `unravel_index` is now used only by the batched `matmul`, once per batch.

Three interleaved runs, one workload per process, `NN_NUM_THREADS=8 taskset -c 0-7`, `--warmup 10`, median total ms (the desktop session was running, so spreads are a few percent; paired ratio = median of per-run new/old). Files: `docs/performance/baseline/v1.1.0/bcast/`.

## Follow-ups

1. Done (see "Broadcast fast path"): `elementwise` is parallel and allocation-free for every broadcast shape; cnn_fer total went from 716 to 165 ms (native, 8 threads).
2. Fuse BatchNorm: compute the statistics in one pass and the normalisation in one pass with a dedicated backward, instead of about ten composed ops per layer. This needs its own gradcheck.
3. Done as part of item 1; `unravel_index` remains only in batched `matmul`, once per batch.
4. Avoid zero-filling and the malloc/free churn of fresh per-step tensors (reuse buffers), which also removes the 2x process-history dependence of cnn_mnist described above.
5. Re-run the thread-count policy: cnn_mnist improves only from 3.2 to 2.7 ms from 1 to 12 threads.

## Caveats

- The governor was `powersave` and a desktop session was running; absolute times are noisy, ratios of paired runs are the evidence. The suite medians in the first guard table have old-vs-old spreads above 3% on most rows.
- Real-data accuracy of `train_fer2013` is not part of this document (FER-2013 is not in the repository).
